# Menara Command Center: Codebase Handbook (Claude Code)

Owner: Izzham Burhan, TMRND. Built for the TM AI Elevate hackathon. **All data is synthetic.**
Other agent platforms read `AGENTS.md`. This file is the Claude Code entry point.

## What this is

A Palantir-style network command center for Malaysia. Each domain is its own MCP server; an ontology links them; an LLM agent (not in this repo yet) reasons over them. This repo currently holds the **MCP side**.

## Skills

Skills enforce the process gates in `playbook.md`. **Invoke them with the Skill tool before the work they guard; do not skip or rationalize around them.**

| Skill | Invoke when |
| --- | --- |
| `menara-workflow` | Starting any task. The mandatory entry point; classifies the task and routes to the rest. |
| `change-intake-discovery` | A non-trivial change where current behavior, owner, contracts, or risks are not yet established. Read-only. |
| `change-design-spec` | Discovery is done; requirements, acceptance criteria, contract, tables, and scenario impact must be decided and approved. |
| `tdd-plan` | The spec is approved; turn it into test-first slices. |
| `implementation-gate` | Code edits are imminent, and at Gate 1.5 to set up the worktree. Confirms workspace, green baseline, and edit boundary. |
| `verification-review` | Implementation is done; produces fresh evidence before any completion claim. |
| `completion-checkpoint` | Work is verified; the developer chooses commit, push, PR, or leave (Gate 6.5). |
| `handoff-summary` | End of any AI-assisted task. |
| `mcp-contract-guard` | Any change under `servers/` or `packages/menara-core/`, or to a tool, model, table, port, or `.mcp.json`. |
| `synthetic-data-guard` | Seed or scenario data, subscriber or location fields, UI copy, or anything that could read as a claim about real TM systems. |
| `doc-drift` | Code diverges from the docs, or a change alters layout, rules, contracts, ports, status, or process. |

Skills live in `.claude/skills/` (Claude Code) with a Codex twin in `.codex/skills/`. Edit the Claude copy, then run `uv run python scripts/sync_codex_skills.py`; CI runs `scripts/check_skill_parity.py` and fails if the twins differ. When in doubt, invoke `menara-workflow` first.

## Process

`playbook.md` is the process: gates 0 to 7, git and branch rules, validation commands, Definition of Ready and Done, review checklist. Short version: classify, discover, set up a worktree, write the spec, write the TDD plan (the developer approves both), confirm the baseline, implement test-first, verify with fresh output, let the developer choose commit, push, or PR, then hand off. Do not commit or push without the developer's say-so.

Worktrees: `sh scripts/worktree-add.sh <branch>` creates `.worktrees/<branch>` so agents can work in parallel; `sh scripts/worktree-cleanup.sh` removes merged ones.

## Layout (monorepo, uv workspace)

```
packages/menara-core/   shared library, not an MCP: envelope, IDs, privacy, clock, audit, tokens, seed
servers/<name>-mcp/     one independently runnable MCP per folder (own pyproject, README contract, src, tests)
data/scenario/          scripted scenarios (kuala_krai.yaml)
data/menara.db          generated by `uv run menara-seed`, gitignored
.mcp.json               registers the MCPs for clients
tests/golden_trace/     agent walk across separate server processes (ticket to Incident, steps 1-6)
playbook.md             the process: gates, git rules, validation, Definition of Done
.claude/skills/         process and guard skills (Codex twins in .codex/skills/)
scripts/                worktree-add/cleanup, skill sync and parity check
.github/                CI workflow and pull request template
```

The folder is `servers/`, not `mcp/`: pytest's importlib mode turns a folder named `mcp` into a package that shadows the real `mcp` library.

## Commands

```bash
uv sync

uv run python -m menara_core.scenario_cli show|set N|advance N|reset
uv run python -m pytest
uv run python -m ruff check .

uv run --package tower-mcp python -m tower_mcp
```

Prefer `python -m ...` over console scripts: some Windows machines block `.venv` `.exe` shims.

## Rules every MCP follows

1. **Separate server.** Depends only on `menara-core`. No MCP calls another MCP; the agent orchestrates.
2. **Own tables only.** Everyone reads `data/menara.db`; each MCP writes only the tables it owns. `menara_core.db.connect(path, owned_tables=...)` enforces it with a SQLite authorizer. No owned tables means a read-only connection. Cross-domain reads of tables another domain owns are read-only and limited: `ontology-mcp`, `twin-mcp` and `policy-mcp` read base tables to compute impact themselves; `ran-mcp` reads `cell` and `tower`; `drone-mcp` reads `tower`; `tower-mcp` and `ontology-mcp` apply `ran_kpi_effect` through `menara_core.kpi_overlay`. Each server's README says what it reads.
3. **Envelope.** Every tool returns `Envelope` with `synthetic: true` and `evidence[]`.
4. **Domain-prefixed tool names** (`tower_get_status`).
5. **Tests first, strict typing.** pytest, ruff, mypy strict. Tool logic lives in `tools.py` as plain functions; `server.py` only registers them.
6. **Pin `mcp[cli]>=1.9,<2`.** mcp 2.x renamed `FastMCP`.
7. **Transport:** stdio by default, `--transport streamable-http` with ports from 8101.
8. **Writes to the real world** go through policy-mcp. Action MCPs verify HMAC policy tokens locally (`menara_core.tokens`).
9. **Data-source layer (pattern, tower-mcp only so far).** `tower-mcp` reads through a `TowerSource` interface (`source.py`) with a SQLite and an HTTP implementation, so moving to real data means writing a source, not rewriting tools. The other servers still query SQLite directly; copy the pattern when one needs a real source. Envelopes from a real source must say `synthetic: false`.

## Privacy and honesty

- Hashed MSISDN (`menara_core.privacy`), cell-level location only, aggregates under 5 are suppressed.
- Label demo data as synthetic. Make no claims about TM's real systems, prices or coverage.
- No real organisation branding in any UI.

## Scenario clock

`t_min` is minutes since T0 (07:00, 2026-11-14, Kuala Krai flood). Move it with `menara-scenario`. The default is T0, when only TK-88213 exists. Tickets, alarms, KPIs and missions appear or progress only as the clock reaches them.

| t_min | What happens |
| --- | --- |
| -240 | Mains fails at `KKRI-0142`; feeder `FDR-KKRI-01` trips |
| -5 | `KKRI-0142` goes DOWN; neighbours `KKRI-0143` and `KKRI-0144` hit 91% PRB |
| 0 | TK-88213 arrives |
| 12 | The ticket storm is complete (37 tickets) |
| 12 to 75 | A drone approved at 12 arrives about 57 and finishes inspecting at about 72 |
| 360 | Power is restored; `KKRI-0142` is UP, alarms clear, loads return to normal |

Whoever drives the demo (the command-center UI or the agent's orchestrator) moves the clock; the servers never do.

## Secrets

`.env.example` lists them. `MENARA_APPROVER_KEY` gates `policy_approve`, `policy_reject`, `policy_update_setting` and turning the kill switch off. **The command-center UI holds it; the agent must not.** The dev defaults are public, so set private values in `.env` for a shared demo. This stops an agent approving its own request; it is not production security.

## Adding an MCP

Run `uv run python scripts/new_mcp.py <name> --port <port> --description "..." [--owns table1,table2]`. It creates `servers/<name>-mcp/` with a placeholder tool and tests, and registers it in `.mcp.json` and the root `pyproject.toml`. Then replace the placeholder (tests first), update the status table above, and follow `mcp-contract-guard`.
