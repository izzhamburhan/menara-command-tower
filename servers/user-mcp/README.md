# user-mcp

Subscriber serving cell, experience, who is on a tower or inside a circle, and where a subscriber has been. **All data is synthetic and PII-masked.** Read-only; owns no tables. Reads `subscriber`, `subscriber_state`, `subscriber_experience`, `subscriber_cell_visit` and, for the population estimate, `tower_subscribers`.

Subscribers are identified only by `msisdn_hash` (a salted 16-hex-char hash; raw numbers are never stored). Location is cell-level, never individual.

## Run

```bash
uv run menara-seed
uv run --package user-mcp python -m user_mcp                          # stdio
uv run --package user-mcp python -m user_mcp --transport streamable-http --port 8103
```

## Tool contract

Every tool returns `{synthetic: true, as_of, data, evidence[], warnings[]}`.

| Tool | Arguments | `data` |
| --- | --- | --- |
| `user_get_serving_cell` | `msisdn_hash` | `serving_cell`, `enodeb_name`, `attached`, `detached_since`, cell-level `cell_lat`/`cell_lng`, plan, segment, `home_fibre`. If not attached, `serving_cell` is the last known cell and a warning says so |
| `user_get_experience` | `msisdn_hash, window_min=120` (5-1440) | `points[]` (score 0-100, label GOOD/FAIR/POOR/NO_SERVICE, throughput, drop events, RSRP), `latest`, `summary` |
| `user_list_in_area` | `lat, lng, radius_km` (0.1-100)`, limit=200` (1-500) | Subscribers whose serving tower is in the circle now: `towers[]` (`subscribers_sampled`, `subscribers_est`), `subscribers[]` (hash, cell, `attached`, `latest_label`, `cell_changes_24h`), `subscribers_total`, `subscribers_est_total`, `returned`, `truncated`, `withheld` |
| `user_list_on_tower` | `enodeb_name, limit=200` | The same shape for one tower |
| `user_get_trail` | `msisdn_hash, window_min=1440` (5-2880) | `window_start`, `segments[]` oldest first (`serving_cell`, `enodeb_name`, cell-level `cell_lat`/`cell_lng`, `arrived_at`, `left_at`, `duration_min` inside the window, `current`), `moves`, `distinct_towers` |

Get the hash from a ticket's `customer_ref` (ticket-mcp) or from a subscriber list.

`user_get_serving_cell` reports the cell from the trail at the current clock, so a commuter shows a different cell once the clock passes their move (at scenario minute 0 it equals the `subscriber` row).

## A sample, and privacy

- The subscribers in the data are a **synthetic sample** (about 6 to 14 per tower, 40 on the flood towers). `subscribers_sampled` counts that sample; `subscribers_est` is the tower's population estimate (for example 820 for `KKRI-0143`). Use the estimate for headline numbers.
- **Small groups are withheld.** If 1 to 4 subscribers match, `withheld` is true and no rows or counts are returned (`menara_core.privacy.MIN_AGGREGATE_COUNT`). No match at all is just an empty list.
- Identifiers are hashed MSISDNs and location is cell level (a tower position), never a point for one person.
- **Real data needs sign-off first.** A person's movement history is personal data under PDPA. All data here is synthetic; do not point these tools at real subscriber data without legal and data-protection approval.

## Trails

Trails come from `subscriber_cell_visit`, generated by the seed (`menara_core/seed/movement.py`) over minutes -1440 to 480. About half of the subscribers who have a work tower 5 to 25 km away commute (home, a tower on the way, work), leaving about 08:00 (minute 60). Subscribers on the flood-cluster towers never move.

**Known limitation:** attach state and experience samples are generated at the subscriber's home tower, so for a commuter they do not follow the move.

## Flood scenario

At clock 12, the TK-88213 customer is on `KKRI-0142-B1`, not attached since 06:55, experience `NO_SERVICE`. Subscribers on the overloaded neighbours `KKRI-0143` and `KKRI-0144` are degraded, not silent. `user_list_on_tower KKRI-0142` shows 40 sampled subscribers (estimate 980), all not attached.
