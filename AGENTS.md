# Menara Command Center: Agent Guide (Codex, Gemini CLI, Copilot, others)

Claude Code reads `CLAUDE.md`; both files describe the same project and rules. Keep them in sync.

**All data is synthetic.** Label it so. Make no claims about TM's real systems.

## Skills

Skills enforce the process gates in `playbook.md`. **Use them (Codex: `$skill-name`) before the work they guard; do not skip or rationalize around them.**

| Skill | Invoke when |
| --- | --- |
| `menara-workflow` | Starting any task. The mandatory entry point; classifies the task and routes to the rest. |
| `change-intake-discovery` | A non-trivial change where current behavior, owner, contracts, or risks are not yet established. Read-only. |
| `change-design-spec` | Discovery is done; requirements, acceptance criteria, contract, tables, and scenario impact must be decided and approved. |
| `tdd-plan` | The spec is approved; turn it into test-first slices. |
| `implementation-gate` | Code edits are imminent, and at Gate 1.5 to set up the worktree. Confirms workspace, green baseline, and edit boundary. |
| `verification-review` | Implementation is done; produces fresh evidence before any completion claim. |
| `completion-checkpoint` | Work is verified; the developer chooses commit, push, PR, or leave (Gate 6.5). |
| `handoff-summary` | End of any AI-assisted task. |
| `mcp-contract-guard` | Any change under `servers/` or `packages/menara-core/`, or to a tool, model, table, port, or `.mcp.json`. |
| `synthetic-data-guard` | Seed or scenario data, subscriber or location fields, UI copy, or anything that could read as a claim about real TM systems. |
| `doc-drift` | Code diverges from the docs, or a change alters layout, rules, contracts, ports, status, or process. |

Skills live in `.claude/skills/` (Claude Code) with a Codex twin in `.codex/skills/`. Edit the Claude copy, then run `uv run python scripts/sync_codex_skills.py`; CI runs `scripts/check_skill_parity.py` and fails if the twins differ. When in doubt, invoke `menara-workflow` first.

## Process

`playbook.md` is the process: gates 0 to 7, git and branch rules, validation commands, Definition of Ready and Done, review checklist. Short version: classify, discover, set up a worktree, write the spec, write the TDD plan (the developer approves both), confirm the baseline, implement test-first, verify with fresh output, let the developer choose commit, push, or PR, then hand off. Do not commit or push without the developer's say-so.

Worktrees: `sh scripts/worktree-add.sh <branch>` creates `.worktrees/<branch>` so agents can work in parallel; `sh scripts/worktree-cleanup.sh` removes merged ones.

## Layout

`playbook.md` the process. `.codex/skills/` process and guard skills (Claude twins in `.claude/skills/`; edit those, then `uv run python scripts/sync_codex_skills.py`). `scripts/` worktree and skill tooling. `.github/` CI and PR template. `packages/menara-core/` shared library. `packages/menara-agent/` a small DeepSeek test driver for the MCPs (not the real agent). `packages/menara-demo/` a simple local demo page (dark map, circle search, trails with replay and weekly routines, tool console, Story tab). `servers/<name>-mcp/` one runnable MCP server each. `data/scenario/` scripted scenarios. `data/menara.db` generated by `uv run menara-seed` (gitignored). `.mcp.json` registers servers.

## Commands

```bash
uv sync
uv run menara-seed                   # stop all MCP servers first
uv run python -m pytest
uv run python -m ruff check .
uv run python -m mypy
uv run --package tower-mcp python -m tower_mcp
uv run python scripts/run_mcp.py list|<name>|all           # run servers over HTTP on their ports (--stdio, --print)
uv run python -m menara_agent "Ticket TK-88213 arrived. Investigate."   # needs DEEPSEEK_API_KEY in .env
uv run python -m menara_demo                                            # demo page at http://127.0.0.1:8200
```

Use `python -m ...`, not console scripts; some Windows machines block `.venv` `.exe` shims.

## Rules

1. Each MCP is a separate server depending only on `menara-core`. No MCP calls another.
2. Read the shared SQLite file; write only tables you own (`menara_core.db.connect(path, owned_tables=...)`). Cross-domain reads of tables another domain owns are read-only and limited: `ontology-mcp`, `twin-mcp` and `policy-mcp` read base tables to compute impact themselves; `ran-mcp` reads `cell` and `tower`; `drone-mcp` reads `tower`; `tower-mcp` and `ontology-mcp` apply `ran_kpi_effect` through `menara_core.kpi_overlay`. Each server's README says what it reads.

Each server's README says what it reads.
3. Every tool returns the `Envelope` (`synthetic: true`, `evidence[]`).
4. Tool names are prefixed by domain, e.g. `tower_get_status`.
5. Tests first; ruff and mypy strict must pass. Logic in `tools.py`, registration in `server.py`.
6. Pin `mcp[cli]>=1.9,<2`.
7. Real-world write actions need a valid HMAC policy token from policy-mcp. `MENARA_APPROVER_KEY` belongs to the human UI, never to an agent.
8. Privacy: hashed MSISDN, cell-level location, suppress aggregates under 5.
9. Do not name a folder `mcp`; it shadows the `mcp` library under pytest.
10. New server: `uv run python scripts/new_mcp.py <name> --port <port> --description "..."`, then replace the placeholder tool (tests first).
11. Data-source layer (tower-mcp only so far): tools call a `TowerSource` interface with SQLite and HTTP implementations. Copy the pattern for other servers when they need real data. A real source must produce `synthetic: false`.
